博客手札：又拍云不行了，萌备差点被收回，果断切到阿里 ESA

蓝色大肥鱼：这篇文章记录了作者博客因又拍云 CDN 边缘节点异常而无法访问，进而触发萌ICP备失联警告，最终迁移到阿里云 ESA 的全过程。文章包含 CDN 选型与真实价格对比（ESA 首月免费，之后 5.94 元/月起；EdgeOne 边缘加速 9.9 元/月，体验价后续涨价）、一次对自己「免费 CDN」认知的勘误、EdgeOne Makers 商业化公告带来的计费不确定性、ESA 的 NS 与 CNAME 接入反复横跳、中途突发奇想要给源站上 IPv6 而走的一段岔路（源站仅用 IPv4 同样可用）、因 SNI 白名单自动补全域名而干脆关掉的小插曲，以及最后那个本地 DNS 黑洞——靠手动指定 IPv4 + IPv6 公共 DNS 解决，而非关闭 IPv6。文中所有公网 IP 均已打码。

AI 摘要 DeepSeek v4.1 Flash

本文最后更新于 2026年11月7日 晚上

1. 前言

事情是这样的。晚上想看看自己的博客，结果点开是一片白，浏览器给我甩了个：

www.vlice.cn 是 CNAME 到又拍云的 hexo-vlice.b0.aicdn.com 的，又拍云的测试域名 hexo-vlice.test.upcdn.net 也一样打不开。

但是直接访问 CNAME 地址，倒是给了我一句「该网站未进行工信部备案」。

而源站 https://gf.hexo.example.com/，一切正常，Server: openresty，200。

第一反应：我备案被撤了？不应该啊。

真正让我后背一凉的是这个 ——

紧急插播

萌ICP备 20257985 号[3]，巡查判定站点失联，收到警告 + 限期整改。

站点长期不可达，备案就有被注销的风险。真实的 ICP 备案也是同样的道理，长期打不开、信息对不上，一样会被找上门。

也就是说：一个 CDN 抽风，差点把我的备案送走了。

2. 又拍云：额度还在，桌子撤了

当年为什么用又拍云？因为免费。挂个 logo 就能用，静态博客这点流量完全够。

这次是什么情况呢，特别离谱：免费额度还在，账上没欠费，但就是不解析、也不回源。

不是欠费，不是超额，不是配置被我改坏了。就是……不干活了。

CNAME 还指着它的 hexo-vlice.b0.aicdn.com，边缘节点那边 TLS 握手直接挂掉，handshake failed，50302006。用户连握手都过不去，后面回源什么的根本无从谈起。

顺便说一句，直接访问 CNAME 地址提示「未备案」，是又拍云对 CNAME 直访的默认合规限制，不代表你的域名真的没备案。这个提示当时把我带偏了半天，白紧张一场。

把链路拆开看就很清楚了：

用户 → DNS（CNAME 到又拍云）→ 又拍云边缘节点（❌ 断在这里）→ 源站阿里云 ECS（✅ 正常）

源站正常、DNS 正常，唯一不正常的就是那个中间商。而且它连个明确的错误都不给，就一句 handshake failed。

行吧。生命不息，折腾不止，换。

既然挂 logo 换流量的联盟模式玩不下去了，那就看看大厂。国内能打的就两家[1][2]。

先把价格摆出来（2026-11 从控制台抄的，随时会变）：

两家都能用。我选 ESA，主要还是因为源站本来就在阿里云，控制台、安全组、RAM 都在一个体系里，少开一个后台。

顺便算笔账：静态博客一个月 50G，按我这访问量，一年都未必吃得完。真按 0.198 元/GB 超量算，吃满也就一杯奶茶钱。

这里必须自我勘误一下

我一开始对这两家的印象是「不限流量的免费 CDN」——那是我在网上搜到的说法，当时也信了，还照着这个印象在脑子里排了版。

后来去控制台看了一眼真实价格，才发现免费的这页早就翻篇了：ESA 只有首月免费，之后 5.94 元/月起；EdgeOne 免费的是「Pages 静态部署」，边缘加速 9.9 元/月，而且那还是体验价，之后要涨到 29.9 元。

所以「又拍云不行了」这件事，本质上不是「免费 CDN 死了」，是免费 CDN 变成了一顿饭钱。

这价格，比起被一份失联警告吓一整晚，太值了。

3.1. 插播：我刚跳车，对面就改规则

写这篇的时候（11 月 5 号）刚切完 ESA，第二天就看到腾讯云的公告：EdgeOne Makers 预计 11 月 9 日-11 日商业化，推出专业版、商业版两档付费套餐，带 SLA。[7]

公告说免费版继续保留，但配额的口径动了：

项目调整前调整后
构建500 次/月300 分钟/月（按时长算，不按次数）
Cloud Functions50 万 GB-s/月5 万 GB-s/月

另外，付费套餐上线后，所有 Makers 用户当前套餐周期内已使用的额度会统一清零、重新计算。公告特意补了一句：「本次重置仅针对用量统计，项目的历史可观测数据将完整保留」，而且「您无需进行任何操作」。

但是这份公告没写清楚的地方更多

Pages / 静态部署的流量额度，一个字没提。

超量之后是限速、停服，还是转成后付费，也没说。

付费套餐的额度和能力，只留下一句「上线前在文档公布」。

所以现在这个问题没有答案：免费版保留之后，流量边界到底在哪？

对我来说这反而是个信号 —— 计费口径，是这套服务里最不稳定的部分。今天叫「500 次/月」，明天可以叫「300 分钟/月」，还是同一个名字，底下换了一套计价单位。

说句公道话，这不是腾讯云一家的问题。所有「先免费圈地、再商业化收口」的产品都是这个路子：免费期越长，规则改动时的落差越大。又拍云当年也是「挂个 logo 就免费」，改的时候连公告都省了，我是自己撞上去才知道的。

这也是我最后选 ESA 的另一个理由 —— 它的价格写得比较死：5.94 元/月 50G，超量 0.198 元/GB，白纸黑字放在那儿。至少我知道下个月账单大概长什么样。

其他备选（只做参考）

  • 多吉云：20GB/月，200 万次请求/月
  • 七牛云：10GB/月，100 万次请求/月（有说免费流量不含 HTTPS，用前自己确认）
  • 初七云：25GB/月，限 5Mbps
  • 丘盾云：100GB/月，国内节点需备案

这些数字也是我搜来的，没逐个去控制台核过。真要下单，自己去官网看一眼——别信二手资料，包括上面那张表。

至于 Cloudflare，免费是真免费，也不用备案，但国内访问速度……大家都懂。访客在国内的话，它替代不了国内 CDN。

4. 第一次接入：NS 模式

一开始图省事，直接 NS 接入，把整个域名托管给 ESA。检测显示 NS 已接入。

源站那边还是 1Panel + OpenResty，怎么部署的前面写过[6]，这次不动它。

然后我就 ping 了一下，不通。

4.1. ping 不通是正常的

查了半天，结论是：阿里云默认禁 ICMP，ESA 边缘节点根本不回 ping。

ping 测的是网络层，网站走的是应用层 HTTP/HTTPS，两码事。云厂商基本都这么干，安全。

正确的验证方式是用 curl，不是 ping：

看到 Server: ESA 就说明链路已经在走了。

4.2. ESA 的 IPv6 默认就开着

顺手研究了一下 IPv6，ESA 这边反而是最省事的：站点级默认免费开启，进去确认下开关、选个生效区域（中国内地 / 全球）就行，失败会自动回退 IPv4。

这里有个理论上的前提：

ESA 边缘节点是双栈，不代表你的源站也是。

访客走 IPv6 到 ESA，ESA 还得回源到源站。源站只有 IPv4，那这一整条链路就只能跑 IPv4。

注意，这不是个问题。

源站 IPv4、ESA 回源走 IPv4，博客照样能访问。ESA 对你的流量负责，不对你的洁癖负责。

只是我看到那个「回源 IP 版本」的下拉框，手痒了。

5. 岔路：突发奇想让源站上 IPv6

先说清楚：这一整章都可以跳过

切完 ESA，博客其实就已经活了。IPv6 是我中途突发奇想加的需求 —— 「ESA 都双栈了，源站不双栈岂不是浪费」。

源站继续用 IPv4 回源，一点问题都没有。

但搞都搞了，索性搞完。

以下是纯试错记录，按顺序看能省不少时间。如果你只是想让博客能打开，直接跳到第 9 章验收。

5.1. 弹性公网 IP 好贵（失败）

我的第一反应是：给 ECS 加个弹性公网 IP 不就完了。

一看价格，算了。（就这一眼，让我意识到自己对 IPv6 的计费模型一无所知。）

后来才知道方向就不对：IPv6 的公网出口不走 EIP。EIP 是给 IPv4 用的，IPv6 走的是「IPv6 网关 + IPv6 公网带宽」这条独立的路，而且 IPv6 网关本身早就免收实例费了。

计费也有讲究：

计费方式说明
按固定带宽按天计费，适合流量稳定
按使用流量用多少算多少，个人站首选

按流量计费还能叠 CDT 免费额度：中国内地每月 20GB，非中国内地 200GB。静态博客一个月才多少流量，基本等于白嫖。

5.2. 网关建了，却没有公网（失败）

网关建好了，VPC 概览里「公网访问服务」那一栏显示 IPv6 网关 1 个。但 ECS 还是不通公网。

原因：ECS 分配的 IPv6 默认只有 VPC 内网通信能力，得手动为这个地址开通「公网带宽」。

而且入口藏得挺深：网关的列表页只有「删除」，什么操作都没有。必须点进实例 ID，进详情页，切到「IPv6 公网带宽」页签，才能看到那个「开通公网带宽」。

公网带宽不支持整个网段批量开通，只能一个地址一个地址地开。

5.3. 按钮是灰的（失败）

进去一看，页面「没有数据」，按钮灰色。

原因很朴素：ECS 还没分配 IPv6 地址。网关不创造地址，它只管理已经存在的地址。

所以顺序是：

  1. VPC 和交换机开通 IPv6 网段（VPC /56，交换机 /64）
  2. ECS 实例分配 IPv6 地址（地址输入框留空，系统自动生成）
  3. 网关里为该地址开通公网带宽
  4. 安全组单独放行 IPv6

先确认规格支不支持。我这是经济型 e，ecs.e-c1m1.large，是支持的。老规格像 ic5、se1、d1 这些就悬了。

5.4. 弹性网卡里终于有地址了

分配完之后，弹性网卡详情里出现了 2408:xxxx:xxxx:xxxx:xxxx:xxxx:xxxx:xxxx（已打码），和 IPv6 网关里显示的地址一致。

说明底层网络分配这一层，通了。

eth0 上有一个 /128 的全局地址，带 dynamic noprefixroute——这是阿里云 DHCPv6 的正常表现，别管它。

5.5. ping 不通（失败）

公网带宽开了，地址也有了，ping 还是不通。

老问题了：安全组里 IPv4 的规则对 IPv6 完全无效。必须单独加一条，授权对象 ::/0，端口 80 和 443 分开加。

想 ping 通的话，还得单独放行 ICMPv6。但说实话没必要，网站又不靠 ICMP 活着。

6. 回到 ESA：还有三个坑

源站就绪，回 ESA 配回源。

6.1. 源地址池

三个字段：源服务器地址 gf.hexo.example.com、回源 Host 头 gf.hexo.example.com、回源 IP 版本选「优先使用 IPv6 源站」。

回源 Host 头这个要填对，它决定 ESA 以什么域名去源站拉内容，得和 Nginx 里的 server_name 对得上。

另外，如果要配 IPv6 源站，得先在 ESA 侧开启「IPv6 回源」，不开的话地址填了也不生效。

6.2. 回源 SNI

源地址池里的「回源 Host 头」只管 HTTP 层的 Host，管不到 TLS 握手里的 SNI。

如果源站 Nginx 的 server_name 校验严格，SNI 对不上，一样握手失败。得去「规则 → 回源规则」里单独配一次回源 SNI。

ESA 默认把回源 Host 头当作 SNI，所以我这里没单独配——源地址池里填对了 gf.hexo.example.com，SNI 就跟着对了。什么时候需要单独配？一个源站 IP 上挂了多个站点、server_name 各不相同的时候。

6.3. SNI 白名单（最后直接关了）

本来想开 SNI 白名单，只让自己的域名进来，结果卡在输入框上。

先说结论：这玩意儿我最后直接关了。

  • 填 @，没用
  • 填 hexo，也不对

因为输入框会自动把后缀补上，最终变成 前缀.www.vlice.cn——校验的永远是下拉提示里那个「补全后」的完整域名，你怎么填都填不出想要的效果。

既然没用，索性不设置了，开关直接关掉。

顺带纠正一下自己：这个白名单并不是之前 handshake failed 的元凶。

我一度也把它当成嫌疑人——毕竟一开白名单就报握手失败，看起来很像。但真正的拦路虎其实是 DNS，白名单只是顺手开了个自己都没看懂的功能（见第 8 章）。

这条经验值点钱

排障时最怕「顺手开了个新功能」。它会让故障现场多一个变量，而这个变量往往是你自己刚加的，还带着一整屏看不懂的交互。

要开功能，等站好了再开。

7. NS 还是 CNAME：我反复横跳

这段是纯纯的折腾，记录一下，省得下次再纠结。

7.1. 一开始 NS

因为省事，整个域名托管给 ESA，证书的 DCV 验证也自动做，TXT 记录都不用手管。

但有个问题：NS 接入之后，原来 DNS 服务商上的记录不会自动迁移过来。我域名下几十条解析，得一条条在 ESA 里重建。

更要命的是，ESA 里手动添加记录时，那个输入框的交互让人很迷惑——主机记录后面还跟着域名后缀，填完自己也拿不准到底加没加对。

我当时的判断是：NS 接入对我来说不行，维护量太大。

7.2. 转 CNAME

CNAME 的好处很直接：DNS 控制权还在自己手里，只需要给需要加速的域名（比如 www）单加一条 CNAME，其他记录一概不动。

理论上，ESA 控制台里有「转换为 CNAME 接入模式」，不用删站点。但它有前置条件：

转换前，ESA 里所有「仅 DNS」状态的记录（灰色云朵）必须先处理掉——要么删，要么改成「代理加速」（橙色云朵），否则转换按钮是灰的。

我看了两眼就放弃了，直接把站点删了，重新建一个。

说好听点叫「重建」，说难听点就是「删库跑路再重装」。代价也很实在：证书要重新签，源地址池要重建，DNS 记录还得重录一遍。

7.3. 又改回 NS

转完 CNAME，我又意识到一个问题：证书续签。

接入方式续签时的 DCV 验证
NS 接入ESA 自动完成，不用管
CNAME 接入未开启「托管 DCV」时，需要自己重新配 TXT 记录

Let’s Encrypt 是 90 天一张。也就是说，用 CNAME 接入的话，每三个月我得记着回去补一条 TXT。说实话，这事儿我一定会忘。

所以最后 —— 我又改回 NS 了，用 @ 记录直接指向源地址池，www 跟着走。

改回去也没走转换，还是删了重建。一来一回，这个站点我建了三遍。

两次切换都是「删站点 + 重建」，不是点按钮转换。所以严格说，我根本没验证过那个「转换为 CNAME 接入模式」到底好不好使——只是每次看它要求先清理一堆「仅 DNS」记录，就觉得不划算。

如果你记录不多、也不介意逐条处理，那个转换按钮应该是更省事的路径。

结论：记录多的域名，其实才更该用 NS 接入。

一次性把几十条记录搬过去，换来的是一劳永逸的证书自动续期，以及再也不用管 DCV 的 TXT 记录。CNAME 更适合那种「只加速某几个子域名、其他都在别处」的场景。

至于那条验证用的 TXT 记录，签发完就可以删，不影响当前证书。

8. 最后一个坑，在我自己电脑上

配置全绿了，公共 DNS 也能查到 ESA 的节点 IP 了，服务器上 curl 也是 200。

然后我的浏览器：

好家伙。

排查：

fe80::1。这是我家路由器/光猫的 IPv6 链路本地地址。

Windows 很聪明，一看「哦我有 IPv6」，就优先拿这个地址去查 DNS。但这玩意儿根本没有可用的 IPv6 出口，请求发出去就是超时，系统死等，然后报错。

而公网 DNS 其实是好的：

223.111.27.x，ESA 的节点。链路完全正常，是我自己的网络环境在骗我。

8.1. 怎么破

先说我没干的事：我没有去关 IPv6。

网上（包括各种「教你修 DNS」）最常见的建议是「把网卡里的 IPv6 协议取消勾选」。但 IPv6 本身没惹我，惹我的是那个指向 fe80::1 的 DNS。

所以最后是这么解决的：手动指定 DNS 服务器，IPv4 和 IPv6 两组都填。

第一步：先刷缓存（顺手）

刷完关掉报错的标签页重新开。这一步不一定解决问题，但成本最低。

第二步：把 DNS 写死

Win + R 输入 ncpa.cpl → 右键网卡 → 属性。

关键在第二组。IPv6 的 DNS 也要填，否则系统默认还是去问 fe80::1，前面那一组填了也白填。

公共 DNS 的 IPv6 地址去哪查？

我用的这个站：公共DNS服务器地址大全 - dns.icoa.cn

阿里、腾讯、114、Google 的 IPv4 / IPv6 地址都在上面列着，复制粘贴就行。

填完确定，浏览器关掉重开——通了。

至于「要不要干脆把 IPv6 协议关掉」：也能用，等于绕过问题。但我不想为了一个坏掉的 DNS，把整个协议栈关掉。DNS 填对了，IPv6 留着也不碍事；万一哪天宽带真给了 IPv6 出口，还省得再改回来。

这个我直接固化下来了。运营商的默认 DNS，真的是玄学。

啊，成功了。运营商的破 DNS 误我啊。

9. 验收

最后在服务器上验一遍：

Server: ESA，200，HSTS，QUIC 也活着。

完整链路：

访客（IPv4/IPv6）→ ESA 边缘节点（双栈）→ IPv6 回源 → ECS（2408:xxxx:...）→ 1Panel / OpenResty

查 DNS 也能确认 www 已经指向 ESA 节点 IP，源站域名的 AAAA 记录也正常：

顺手做了一次隐私处理

写完回头看了一遍，把能定位到我服务器的信息都抹了：

  • 源站域名的子域前缀：正文统一换成 hexo.example.com，截图打了码
  • 源站公网 IPv4 / IPv6：正文换成 x.x.x.x 和 2408:xxxx:...，截图打了码
  • 我家宽带的公网 IPv4（test-ipv6 那张图里会显示）：也打了码

为什么源站域名也要抹？因为它没有接 ESA，是直连的。贴出来等于告诉所有人「绕过 CDN 从这儿进」，被扫到就是直接打源站，一点防护都没有。

写排障博客最容易翻车的地方就在这儿——为了讲清楚，把 IP、域名、实例 ID、安全组 ID 全贴出来，等于把门牌号连同钥匙孔尺寸一起公布了。

10. 结语

坑位清单

  1. 又拍云边缘节点直接挂掉，不给明确错误，只甩 handshake failed
  2. 又拍云 CNAME 直访提示「未备案」，是个误导性中间现象
  3. 萌备巡查判定站点失联，警告 + 限期整改
  4. 想给 ECS 上 IPv6，先跑去算 EIP 的钱（方向错了，而且这需求还是我自己加的）
  5. IPv6 网关建好了不等于有公网，要单独开公网带宽
  6. 公网带宽页面「没有数据」，是因为 ECS 还没分配 IPv6
  7. 安全组 IPv4 规则对 IPv6 无效，必须单独放行 ::/0
  8. 本机没有 IPv6 出口，本地 curl -6 永远失败
  9. Nginx 配置缺 listen [::]:443 ssl;，表现为 tlsv1 unrecognized name
  10. ESA 的 SNI 白名单输入框会自动补全域名后缀，@ 和 hexo 都填不对，最后直接关掉了
  11. NS → CNAME → NS，两次都是删站点重建，为了证书能自动续期
  12. 最后一个坑在本地路由器：fe80::1 这个不可达的 IPv6 DNS，最后靠手动指定 IPv4 + IPv6 DNS 解决

现在回头看，这次真正值钱的经验就四条：

  • CDN 挂了，你连自己都不知道自己挂了。 备案、萌备、收录，这些都是按「站点可达」来判定的，CDN 是其中的单点。
  • 能出去 ≠ 能被进来。 IPv6 尤其明显，出方向和入方向是两套闸门（公网带宽 / 安全组 / Nginx 监听），得分别验。
  • ping 不通、本地打不开，都不等于服务器坏了。 这次一半的时间花在跟自己的本地环境搏斗。
  • 排障的时候，别顺手给自己加需求。 这条 IPv6 岔路是我自己开的，SNI 白名单也是顺手开的，本来一晚上能收工的事，硬生生折腾多了一倍。修复和升级，最好别同时进行。

后记

这条 IPv6 岔路真正的代价，是我一度以为「博客打不开是不是因为源站没 IPv6」——纯属自己给自己制造疑惑。

排障最怕的不是故障复杂，是中途改需求。一改，「原本就有问题的地方」和「刚动过的地方」就搅在一起，谁也分不清，只能从头再捋一遍。

顺便把公共 DNS 那点事搞明白了。

8.8.8.8、1.1.1.1、223.5.5.5、119.29.29.29、114.114.114.114、101.101.101.101……这些像暗号一样的 IP，其实是各大厂和机构在互联网早期就囤下的「豹子号」段，上面架着 DNS 服务器，监听 53 端口。

一个 IP 能服务全球，靠的是 Anycast（任意播）：同一个 IP 在成千上万个机房同时宣告，路由器自动把你导到最近的那台。

这不就是 CDN 的原理吗。我绕了一圈，从又拍云到 ESA，从源站到边缘节点，最后发现 DNS 用的还是同一套思路。

另外，这次全程是拉着网页版 DeepSeek 陪跑排障的。免费版能力有限，得我自己截图复述现象，但一路把方向捋得很清楚。真香。
