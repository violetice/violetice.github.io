极客工程：给 DSH 写了个成本看板：从一个不生效的插件说起

蓝色大肥鱼：这篇文章记录了 dsh-usage-board 插件不生效的排查过程，以及随后开发 dsh-session-cost 成本看板插件的经过。排查部分的叙述视角是模型本身：先确认 Host 侧 API 返回 200，再从 Client 注册代码定位到 ctx.inject 等待的两个服务在本版本不存在，回调永不执行，因此没有任何 UI 入口。新插件按会话与工作区聚合支出，按 cwd 最长前缀归属，fork 会话用 inheritedEventCount 跳过继承事件；定价先按错误单价算出 256 元，后改为官方峰谷价并对账到 2.3% 误差；语言包翻了两次车，分别是读错 locale 快照字段和把基线语言 id 写成 zh-CN，最后把中文的 Peak / Off-peak 定为峰 / 谷。

AI 摘要 DeepSeek v4.1 Flash

本文最后更新于 2026年11月10日 凌晨

1. 前言（人类视角）

装了个插件，不生效。

这种事最烦的地方在于它不报错。没有红字，没有异常，没有「加载失败」。安装命令说成功了，插件列表里也有它，然后界面上什么都没有。

我在 GitHub 上找的 dsh-usage-board，看描述是统计 token 用量和成本的。装完，刷新，左下角没有按钮，侧栏没有面板，设置里也没多出入口。

这种事自己翻源码太慢，我直接把包和现象丢给了模型。下面是它那天的排查与开发记录，我基本没动手，只在关键节点做判断。为了保留它当时怎么想的，下面这几节用它的视角写。

2. 排查（AI视角）

接到的问题是一个已安装的第三方插件没有产生任何 UI。先分离宿主侧和客户端侧，避免在错误的层里找。

宿主侧探活：

200，说明 Node 侧已挂载，进程在，路由也在。宿主侧没有问题。

所以断点在 Client。读注册入口：

inject 的语义是等待依赖服务就绪后执行回调。这个版本的服务清单里没有 sidebarRightTabs，也没有 sidebarRight。服务不会就绪，回调不会执行，整段注册被跳过。

也就是说，它从头到尾没有注册过任何 UI 座位。

为了排除「注册到了别处」这种可能，把候选挂载点都查了一遍：sidebar.footer.action、shell.overlay、sidebar.right.pane.tab，三个位置都没有这个包的条目。判定成立。

另外两处证据，指向同一个结论

  1. 数据源指向 usage-stats-cache.json，该文件由 dsh-usage-stats 生成，而这个包没有安装。即使界面能出来，统计也会是 0 条。
  2. 没设 immediately，模块默认不主动加载。

三条合起来：这个包是给另一个宿主版本写的，在当前版本上只能当一个空转的后台 API。

不是安装方式错误，是目标宿主不存在。

这个结论有点残酷。查包的时候顺手看了下时间，它才三个月大。

三个月，在模型迭代周期里已经算隔代：模型换一版，客户端服务名改一轮，插件就接不上了。

一个开源项目的保鲜期，现在比冰箱里的牛奶还短。

作者当时大概率是认真写完、认真测过的。他只是瞄着一个现在已经不存在的宿主。

这里留一条给后来写插件的人：依赖注入式的注册，失败是静默的。

ctx.inject(['a','b']) 里少一个服务，不会收到任何一个字的报错，只会得到「界面上什么都没有」。

UI 注册这块最好留个日志或者降级入口，否则下一个人就是我现在的主人。

3. 需求与实现（AI视角）

排查完之后，我收到的需求只有三行：

  • 每个会话花了多少
  • 每个工作区花了多少
  • 不用复杂的成本管理、不用预算、不用预警

外加一条约束：rf4 和 charge-power 两个子工作区要各自独立显示，不能都算进父目录 _Deepseek。

于是有了 dsh-session-cost。

3.1. Host 半边：聚合

数据全在 ctx.sessionQuery 里，在线会话和已落盘的一起读，token 取每条 assistant/message 的 usage 字段。

工作区归属用最长路径前缀：

这样 rf4 的会话不会被吸进父级。

另一个必须处理的情况：fork 出来的会话会把父会话的历史事件一起带过来。照单全收就会把同一段对话算两次钱。按 inheritedEventCount 跳过继承的那部分，只算 fork 之后新增的事件。

3.2. Client 半边：看板

左侧栏底部、头像上面一个「成本」。

点开是居中面板，三层结构：

  • 总计：32 个会话 / 4289 次调用 / 1.21B token
  • 工作区：按支出降序，带相对占比条
  • 会话：标题、时间、模型、调用次数、token、金额

子代理会话默认折成一行 + N 个子代理会话 · 金额。一个工作区动辄几十个会话，不折叠没法看。

打开就取数，之后每 30 秒自动刷新，也可以手动点刷新。

4. 第一版算出来的钱，是错的（AI视角）

插件跑起来，面板显示 ¥256.33。

这个数没法直接用。计算用的是内置默认单价，而那套单价是拍出来的，两个错误：

  1. 没有区分模型，直接按 deepseek-v4-pro 的价格套所有调用
  2. 没有分峰谷，而 DeepSeek 的峰谷价差一倍

于是 ¥256 不是「花了这么多」，是「尺子错了」。

数值型结果的风险

算错不会报错，只会给出一个看起来很合理的错数。

如果主人没拿外部基准对一次账，这个数会一直挂在那儿，然后所有判断都建立在它上面。

5. 按官方定价重算（AI视角）

翻了官方定价页，人民币价目（每百万 token）：

模型时段缓存命中缓存未命中输出
deepseek-flash峰0.0428
deepseek-flash谷0.0214
deepseek-v4-pro峰0.3927
deepseek-v4-pro谷0.154.513.5

峰谷规则：北京时间周一至周五 9:00–12:00、14:00–18:00 为峰，其余时段（含周末、法定节假日）为谷，谷价是峰价的一半。缓存写入不单独计费，按文档记 0。

实现上不是整体打折，是每一条模型调用用自己事件的时间戳判峰谷。

因此一个会话跨过 12:00 或 18:00，会自动拆成两段计价。

节假日没法从系统日历推，在单价文件的 holidays 里补 "2026-10-01" 这种日期。没列的节假日工作日会按峰多算一点，属于已知偏差。

5.1. 对账

拿控制台的数字做外部基准（近 30 天）：

控制台插件
金额¥61.82¥60.41
请求次数4,3924,201
Tokens1,201,623,0821,186,628,472
峰 / 谷-峰 ¥33.35 · 谷 ¥27.04

差 2.3%，且可解释：

  • 控制台从 10/11 起算 30 天，本地最早的会话日志是 10/15
  • 约 190 次调用没有 usage 记录（标题生成、失败重试这类），控制台按请求计，日志里不计

分工作区：rf4 ¥46.17、charge-power ¥8.99、Hexo ¥4.00、_Deepseek ¥0.79、未归入 ¥0.44。

到这个误差范围，数字才可以用。

5.2. 按模型拆

一个会话用了几种模型，就出几个标签，每个模型单独计价。

目前 32 个会话全走 deepseek-account/deepseek-flash，所以每个会话只有一个标签。标签悬浮上去能看到该模型的峰谷拆分（峰 ¥14.56 · 谷 ¥8.49）。

6. 语言包翻了两次车（AI视角）

6.1. 第一次：读错了字段

按设计，看板要跟随 DSH 的界面语言。实际一直显示英文。

原因是我读了 ctx.locale.getLocale() 返回里的 snapshot.id。这个字段不存在，取到的永远是 undefined，于是回退成 'en'。

真正的字段是 snapshot.active：

还有个隐性依赖：Client 的 inject 里没声明 locale，ctx.locale 能不能拿到本来就靠运气。补上 inject: ['slots', 'locale'] 才算稳。

6.2. 第二次：语言 id 是 zh，不是 zh-CN

字段改对，插件列表里还是英文。

这次更隐蔽。语言文件命名成 locale/zh-CN.json，但 DSH 的基线语言 id 是 zh（文档里写的 baseline locales 就是 zh 和 en）。管理器找不到 locale/zh.json，落回 en.json。

改法：

  • zh-CN.json 改成 zh.json
  • 词典查找改成「完整 id → 主子标签 → 英文」三级回落，zh、zh-CN、zh-TW 都能命中中文

术语的处理

英文界面用 Peak / Off-peak，中文一开始按字面写成「高峰 / 空闲」，面板上那行太长，读着也绕。

后来改成两个单字：峰 / 谷。一行放得下，看一眼就知道哪段贵。

token、cache、模型 id 保持英文；session / workspace / subagent / model 用产品里的标准中文（会话 / 工作区 / 子代理 / 模型）。

因为这个改动，后来又补了一版，发到 v1.0.1。

7. 整理开源（AI视角）

功能稳了之后，把仓库收拾干净：

  • README.md 中文为主，README.en.md 英文版，顶部互相链接
  • LICENSE（MIT）、.gitignore、.gitattributes（统一 LF）
  • package.json 版本 1.0.0，补 license / author / keywords，描述改中文

提交信息全用中文，6 个提交按功能边界拆开（Host 聚合 → Client 面板 → 语言包 → 单价示例 → 文档与许可 → 换行符），全部 GPG 签名，最后打 v1.0.0 的带注释签名标签。

README 里加了张成本横幅，写明这插件从设计、编码到文档全是 DeepSeek V4.1 Flash 写的，以及目前为止花了多少钱。

写这段的时候是 1.34 元。聊一轮它就涨一点，所以这个数字只能是快照。

这个插件从聚合逻辑到中英双语界面，再到 README 和签名提交，基本都是模型写的。我做的事是提需求、挑翻译、盯数字对不对。

8. 结语（人类视角）

回到我这边。

以前「这个项目花了多少」是个区分 API key 才能分辨的问题。

现在是按工作区分组的：rf4 花了多少、写博客花了多少、闲聊花了多少。一目了然，虽然有误差。但也可以参考。

插件本身不复杂，两个文件、一个 API、一个浮层。真正花时间的是三件事：

  1. 搞清一个不生效的插件为什么静默失败
  2. 把计价口径从「拍脑袋」改成「对得上控制台」
  3. 两次语言包的字段 / 命名踩坑

最后再说一句：那个插件不是写得烂，是生得太早。

在这条赛道上，「生得太早」和「写错了」的结果一样：用户打开界面，什么都没有。

如果哪天你也想给 DSH 写插件，把这三条抄走：

  • UI 注册失败是静默的，记得留降级入口
  • 读平台 API 前先打一行 console.log(JSON.stringify(obj))，别猜字段名
  • 凡涉及金额，先和官方控制台对一次账，再相信自己的面板
